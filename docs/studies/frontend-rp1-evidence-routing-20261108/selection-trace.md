# P48 Design return: selection and URL trace

P48 remains a **native failure for the selected-part return**. The preserved [run record](../../../runs/frontend-evidence-route-verified-native-20261108/record.json) and [immediate AX capture](../../../runs/frontend-evidence-route-verified-native-20261108/Design-return.ax.txt) show the actual Engineering link navigating to exact RP1 AD1 v2 Design with `part=forward_ring`, specification `811b3bed…4631660`, and `connection=recovery`. The [settled AX capture](../../../runs/frontend-evidence-route-verified-native-20261108/Design-return-ready.ax.txt) and saved image show the same design/spec/connection, but no `part` in the browser address and the Vehicle summary in Details. The run records no input between those two captures. Earlier P48 captures confirm the two explicit ring links and loaded Recovery evidence; they do not turn this return into a pass.

## Source sequence and causal boundary

1. `App.tsx` initializes `vehicleId` from the URL, fetches the inspection source, and calls `resetVehicle()` at the start of the vehicle-load effect. That store action sets `selectedId: null` (`App.tsx` around 183–214; `store.ts` around 138–158). This is expected during load, but it means selection and URL hydration have separate lifetimes.
2. Once a vehicle exists in Design, the route effect reads the part link and calls `select(link.part)` when the link is valid. It then subscribes to **every** later `selectedId` change. The subscription calls `partHref(currentHref(), vehicle, state.selectedId, mode)` and `history.replaceState` (`App.tsx` around 216–230). `partHref` deletes `part` whenever its part argument is null (`partLinks.ts` around 33–57).
3. A transition to `selectedId: null` while that subscription is active therefore produces precisely the observed settled URL: `part` is deleted, while the unrelated `connection=recovery` and exact `spec` parameters remain. `InspectionPanel` derives its part directly from `selectedId`; null displays Vehicle summary (`InspectionPanel.tsx` around 752–806). No source mismatch or invalid-part notice is needed for this result.
4. The subscription also calls `setHref(next)`. On the next route-effect pass, `readPartLink` sees a URL without `part`, and the conditional `if (link.notice || link.part !== null)` does **not** reselect anything. The null selection and shortened URL then persist.

This establishes the **writeback mechanism**, not the exact origin of the null store transition. Source candidates are the vehicle-load `resetVehicle`, explicit clear/selection actions, or the 3D Canvas `onPointerMissed={() => select(null)}`. No Escape, other explicit input, or source mismatch is recorded in P48 between the captures, so the available evidence does not identify which callback fired. The link itself is correctly formed; changing `rp1ConnectionDesignHref` or relaxing part validation would miss the writeback failure.

## Bounded repair and proof

Treat a valid route part as pending until the matching source has loaded and route selection has been applied. During that pending phase, a null store state must not overwrite the valid part in the address. Once hydrated, selection changes from explicit user actions may update the URL normally. Keep the exact config/spec/part validation and invalid-link notice; do not silently restore a foreign or stale part. The existing store subscriber should not be a competing writer while vehicle loading or route hydration is unsettled. The primary agent owns the code decision and P49 sequencing.

A meaningful source test should mount `App` under its actual React `StrictMode` with a valid RP1 URL containing `part=forward_ring&connection=recovery`, defer catalog and vehicle responses in both completion orders, then assert after all effects settle that **both** the Details inspector and browser URL still select `forward_ring`. It should also exercise an explicit Clear selection and assert that only then the part is removed, plus a wrong-spec/foreign-part route that remains unavailable. A native P49 retake, under the existing Chrome owner and packet bounds, is still needed to establish the actual UI behavior; source tests and this trace cannot qualify P48 retroactively.

Frozen RP1/AD1/D1, unadopted FP1/FR1, all five UNSENT inquiries, and engineering, physical, build, and flight gates are unchanged.
